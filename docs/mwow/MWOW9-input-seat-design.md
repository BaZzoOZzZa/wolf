## Proposed ownership and small internal interfaces

**One seat belongs to destination RunScope L**, not to source client run S/T or its connection. For standalone play L=S; for an admitted lobby member L is the exact lobby run. Capture L through F6/F7 membership validation plus a coordinator-owned binding revision; never infer L from numeric session membership alone. A queued command retains S, connection, L, backend generation and grant identity. Changing membership must revoke/fence the old binding before mutating shared input targets. A snapshot lookup alone is not a transaction with current join/leave.

L retains one Xbox model, backend handle and fresh strong `DeviceGeneration` for its game lifetime. Source sessions retain only seat/grant references. No controller Arrival, mask loss, network Pause/Stop or S→T handoff destroys/migrates/recreates this pad. Explicit L RunEnded/shutdown initiates separate owned retirement; Unknown cannot authorize replacement. Legacy source pads must not be silently adopted into this route: require a fresh explicit protected-seat startup, or a separately reviewed migration with proven state. Other legacy routes remain unclaimed, not globally rewritten.

Wire `controller_number=0..15` stays valid. Proposed opt-in policy fixes one selected wire slot (default **0**, configurable per explicitly authorized grant before admission); that slot maps to the same destination Xbox. Valid unselected slots are reported as policy-filtered and cannot create devices. Arrival type/capabilities cannot switch the MVP device model; Xbox-supported analog sticks/triggers/buttons only. Inactive mask of selected slot queues full checked neutral and retains device/owner; it never falls through into pressed-state dispatch. Slot change is a revoke/neutral/grant transaction, never inferred from first input. Generic 16-slot parsing and existing non-MVP behavior stay intact.

Illustrative contracts, not compiled declarations (C++20, no new public wire fields):

```cpp
struct SeatBinding { RunScope source, destination; ConnectionScope connection;
                     BindingRevision revision; }; // strong, coordinator-issued
struct InputGrant { SeatBinding binding; DeviceGeneration device;
                    GrantToken token; uint8_t wire_slot; PeerToken peer; };
struct InputEnvelope { std::shared_ptr<const InputGrant> grant;
                       OwnedValidatedPacket packet; InputOrigin origin; };
enum class Admit { Accepted, Stale, Revoked, Busy, Capacity, Unsupported };
struct WriteReceipt { DeviceGeneration device; uint64_t sequence;
                      WriteOutcome outcome; size_t accepted_events; int error; };
// WriteOutcome = KernelFrameAccepted | Failed | Unknown; not game delivery.
struct TransferHandle; // shared owner of immutable old grant, drain ticket, fence state
class InputSeat {
  Admit submit(InputEnvelope); // copies/validates before enqueue; no device I/O
  RevokeHandle revoke(std::shared_ptr<const InputGrant> expected); // nonblocking latch
  // grant is private to coordinator; backend writers private to worker
};
class HandoffCoordinator {
  TransferHandle begin(AuthorizedTransfer); // internal capability, expected old/new + L
  TransferStatus inspect(const TransferHandle&) const; // no lookup by stable ID
};
```

`GrantToken`, `BindingRevision`, `DeviceGeneration`, `PeerToken` are retained fresh allocation identities, not counters/IDs supplied by clients. ENet reconnect of the same ConnectionScope still needs a new PeerToken; old sender cannot borrow a new grant. Tokens are internal/nonserialized, following RunScope conventions. Coordinator is explicitly shared by ingress/lifecycle/consumer setup, outlives transfer records, and holds `shared_ptr<ConsumerRuntime>`. The existing `ConsumerDrainTicket` remains a value with `shared_future`; a `shared_ptr<const TransferHandle>` owns the **exact saved ticket** and immutable old scope. No parallel registry or shadow consumer model.

### One admission gate and serial executor

ENet authenticates/decrypts/validates first, then submits a captured server-issued grant. Unix input uses the same submit path after existing socket-access checks and packet validation (these are not a new authentication guarantee). It cannot treat an empty ControlPeer as permission to bypass the seat. Proposed default for protected seats: **deny Unix injection unless local delegation to an existing grant was explicitly configured**; approved delegation is stamped at ingress, does not create/take over ownership. Existing JSON has no generation field, so a request first received after handoff cannot reveal that its author prepared the numeric ID earlier. This protocol limitation must be explicit; queued-before-revoke requests can and must be rejected. No invented generation field/takeover endpoint in this task.

Admission and revoke linearize under the same short mutex; device I/O is outside it. Before each side-effect batch the worker checks retained grant/binding/backend against active identity. Revocation marks the grant closed immediately. A batch already reserved as in-flight may finish (cannot cancel a syscall); queued old batches are discarded. Fence succeeds only when that reservation has retired, queues are purged, and all backend-owned writers are accounted for. No eventbus/ENet/HTTP callback waits on this fence. Validation/authentication/replay guards remain before dispatch; successful enqueue is never a kernel receipt. Allocation/queue failure returns refusal; it must not silently drop revoke.

Policy proposal: one worker per admitted MVP seat; FIFO normal queue **256 packets / 64 KiB**, both counted including owned payloads; preallocated revoke latch and one pending-transfer slot outside this budget. No arbitrary coalescing of button edges. Capacity closes admission and schedules revoke/neutral because losing a release is unsafe. At most one active and one pending grant per seat; duplicate transfer identity shares its handle, competing request gets Busy. MVP supervisor cap: **one protected destination seat**, including Unknown retained seat, so a stuck writer cannot cause replacement-thread/device accumulation. This is a cap on the opt-in route, not all-route game singleton enforcement.

### Joint fence: exact order and failure behavior

1. Authorized coordinator reserves the transfer record before mutation. Under seat gate: close old input and feedback admission, latch revoke, capture old identities; pending new owner has no input/consumer grant. Schedule old consumer `revoke(old.connection)` immediately and **save its returned ticket while old scope is still current** (or already has a retained record). This may drain concurrently with input cleanup. Missing/exceptional ticket closes the transfer as Unknown; no fresh lookup or empty-status inference.
2. Worker retires the actual in-flight write, discards old queued commands, stops/fences any permitted backend repeat writers, and obtains feedback-send fence (below). Then it emits full checked neutral for every backend ever admitted in this grant and records receipts tied to L/device generation. A neutral command is not queued behind an unbounded input flood.
3. After neutral receipts are successful, require `saved_ticket.connection.matches(old.connection)` and `saved_ticket.complete()`. Ticket covers both admitted audio/video jobs, and a current-scope zero-worker tombstone is valid. HTTP accepted, EOS, status missing, Stopped label, handler return or future exception is not this proof. F8/F9 holder retirement/join semantics remain unchanged. It is fine if consumers completed earlier; **grant** still follows the input fence and neutral.
4. Coordinator revalidates authorized target connection/peer, L, binding revision, game lifecycle and backend generation while committing the new grant. Publish routing/feedback together with grant in its serial domain. New consumer admission must also wait behind this transaction; existing ANNOUNCE/start paths need the prepared-connection gate before reaching ConsumerRuntime. If any state changed, no grant; retain neutral/quarantine and require explicit reconciliation.

Why not wait for consumers before neutral? A stuck Gst/GPU call must not postpone attempting to release held input. Why not grant after neutral alone? Old consumers/callbacks still own resources and could race a new connection. No lock used by worker/backend/ENet is held while waiting on either completion. Resume replacement, Join/Leave and UI-combo routing must call coordinator, not mutate input objects around it. Pause/Stop only revoke the relevant connection; **never GameStop/RunEnded, silent Leave, or stop_when_everyone_leaves**.

Proposed decision deadline **5 s** from revoke, monotonic, shared across this transaction (no per-step reset). On expiry publish typed Unknown/Quarantined and deny reuse/admission; keep worker, backend, scopes and ticket alive. No detach, forced close, forcekill or replacement pad. It bounds the decision, not a kernel/GPU operation or physical neutral latency. Late completion may supply evidence for an explicit reconciliation attempt; no surprise automatic grant. Failure/partial neutral remains non-success even if consumers drained. A pending connection that dies cannot be granted. Authenticated transport loss/explicit revocation is a trigger; lack of changed input is not. Raw ENet DISCONNECT is currently unauthenticated (`control.cpp:239–245`); do not turn it into a global or newer-owner revoke. A loss notification must identify the already admitted grant/peer, and its trust/timeout policy needs review. Long-held stick with healthy authenticated transport stays held, raw/replayed packets cannot renew authority.

## Checked Xbox seam — proposed tracked patch only

A Wolf wrapper around current void methods is insufficient. Recommend an additive checked snapshot API in pinned inputtino, exposed via a narrow Wolf `CheckedXboxBackend`. It writes through the **same retained uinput device**, not a second descriptor/device or a fresh /dev lookup. At each event, use `libevdev_uinput_get_fd` on the retained handle and a narrow injectable raw-write function returning `{bytes, errno}`. Production calls `::write` exactly once per `input_event`; compare with `sizeof(input_event)` before acknowledging. Do not use the libevdev convenience result as proof of exact bytes. Descriptor reuse is excluded by the retained backend generation and owner lifetime.

Neutral force-writes all configured capabilities regardless of cached button state: 11 EV_KEY buttons=0, HAT0X/Y=0, X/Y/RX/RY=0, Z/RZ=0, then SYN_REPORT=0 (**20 events** for current Xbox definition). Regular snapshots also use one complete frame with final SYN_REPORT, preserving current button mapping and range conversions (including safe Y inversion/clamping at -32768). Last-confirmed cache advances only after all exact writes including SYN. Missing backend, wrong generation, EAGAIN/EINTR/error, zero/short write or exception cannot return accepted. Record progress/error; already emitted effects cannot be rolled back. No attempt to write the remaining bytes of a partial `input_event` as a new event. Conservative MVP: quarantine on any such failure, with bounded explicit recovery allowed only by a later policy decision. Full neutral is idempotent; relative movement/scroll/text is not replayable recovery state.

For Xbox feedback, patch factory to install one immutable router callback **before** publishing/starting listener; never call unsynchronized `set_on_rumble` during handoff. Existing factory signatures/void API remain compatible for other callers, but protected seat uses checked API exclusively. Provide Xbox-specific owned listener stop/retirement with synchronized stop state and join acknowledgement; no detached lifetime claim. Join belongs to the backend retirement owner, never control callback. If a listener cannot retire, retain/quarantine its backend. Changes touching shared BaseJoypadState must account for Switch callers explicitly; do not silently claim its lifecycle fixed. Thread start/allocation failure must roll back unpublished resources. An additive checked factory can preserve legacy behavior while making the new path explicit; exact patch API/layout requires dependency review before coding.

Proposed future files: inputtino `include/inputtino/input.hpp`, `src/uinput/{joypad_xbox.cpp,joypad_utils.hpp,include/inputtino/protected_types.hpp}` plus new internal checked-event writer; tracked Wolf `patches/inputtino-checked-xbox.patch` and separate verifier `cmake/PatchInputtinoCheckedXbox.cmake`. Pin full fd136cfe SHA + pre/post hashes of **every touched file**, verify absent/patched state idempotently, reject unknown/partial content. Compose after the existing signed-motion verifier; do not rewrite it. Source overrides verify-only, no cache surgery/manual include overlays. Build-file/dependency ownership requires Manager's separate grant. This checkpoint does not apply a patch.

### Feedback fence

Persistent callback captures stable router (no raw ENetPeer or source-session peer). Router owns no cycle back to pad; callback lifetime is covered by backend retirement. At intake, feedback is tagged with device generation and current GrantToken/wire slot; the bounded queue retains that tag. It cannot be relabelled on handoff. Router is muted during revoke; no cached effect replay to new grant by default. A later callback from the same persistent game may represent a continuing game effect; inputtino FF has no source ConnectionScope provenance. This is destination-game feedback, not proof of which client caused it.

Control outbox must recheck grant/peer token immediately before encryption/send, in addition to existing V2/current-source/nonce checks. Acquire a send reservation from the same revocation gate, then send only on ENet owner thread. Revoke waits asynchronously for previously reserved sends to retire; queued old grants are dropped. A callback paused after copying the old binding can neither enqueue nor send after revocation. Only then may coordinator publish the new feedback binding. This promises no **new old-peer send after grant**, not recall of UDP packets already sent or physical rumble delivered later. The old transport can receive a best-effort zero-rumble before retirement if policy allows; its delivery is not the neutral-input fence. No blocking ENet callbacks or router lock across an awaited acknowledgement.

## Keyboard/mouse/touch: explicit boundary, no bypass

The worker must gate all packet categories including text, pen/touch, controller motion/battery, UI combo and Unix injection. For keyboard, track actual physical and synthesized keys, aliases and modifiers in a destination ledger; the shared `held_modifiers` byte alone cannot establish releases. For pointer, release all held buttons; relative motion/scroll has no held neutral, but queued motion must be fenced. Touch requires contact cancellation/frame; pen requires tool/contact/button release. A destination change/destructor must not issue out-of-gate release writes.

Two review choices, with **A recommended for the first protected-seat implementation**:

* **A — opt-in PadOnly seat from a fresh admitted run.** Reject keyboard/mouse/text/touch/pen and unsupported pad extensions on both ingress routes before side effects; no repeat backend or pending compositor input may predate admission. Require that backend inventory/attachment precondition explicitly, not “pressed set is empty”. Other routes cannot attach/mutate these inputs for L. This is a documented feature restriction for this opt-in mode, not a global protocol change. It may be insufficient for WoW login/chat/bindings; product approval required.
* **B — mixed input.** No handoff grant until all backends have checked fences. For uinput keyboard, first own/cancel/join repeat execution and add checked release receipts. For Wayland, pin the deployed plugin and add ordered command/fence acknowledgement from the actual compositor after processing all old input and neutral, with retained backend generation; Gst true/queued-to-channel is inadequate. This likely needs separately owned gst-wayland-display/core changes and tests. It still does not prove Wine/game consumed them. Until then mixed-input handoff must fail closed, not pass a pad-only receipt as “all input neutral”.

## Explicit transfer ingress, and separate device executor

For `multi_user=false`, T cannot join occupied L through ordinary JoinLobby; first input is neither authorization nor a transfer request. Required **internal** `AuthorizedTransfer{L, expected_old_grant, candidate_connection, authority, policy}` arrives from a separately approved trusted coordinator action. It must reserve candidate admission without running legacy join side effects, fence S, then commit membership/binding for T and retained destination seat. It must not use ordinary Leave (which migrates pads/restores targets and may stop an empty lobby). Failed transfer retains old membership resources as non-authoritative/quarantined; source-run association and session membership cleanup need explicit reconciliation. F6/F7 remains the minimum guard, but multi-object atomic commit is a separate implementation gate.

Product trigger unresolved: explicit local administrator transfer, or authenticated paired-owner consent/resume policy. Neither is supplied by existing input packets, PIN alone, HTTP input success, authenticated ENet Resume notification, nor current JoinLobby behavior. Same-client REST resume also needs the fence and an explicitly accepted authorization policy before it can activate new consumers/input. Implement low-level fence tests without inventing a public endpoint or UI. Manager must choose trigger/policy before ingress implementation; no silent takeover.

Future `DeviceExecutor` is a separate bounded worker/queue owning Docker I/O and acknowledgements `{destination RunScope, DeviceGeneration, ContainerGeneration, operation identity}`. InputSeat owns kernel state/feedback, not Docker exec or container lifetime. One persistent pad is attached once to L; source handoff requests no unplug/replug. Device readiness must be confirmed before initial grant, and future actual attachment migration needs its own exact completion fence; current PlugDevice event acceptance is insufficient. Unknown Docker result retains resources/no retry under another ID. Count/bytes/cancellation/reserved control lane and reconciliation need their own review; no executor implementation here.

Retained member handling, all-route singleton/prefix aliases, atomic lifecycle admission, all-route input exclusions, crash recovery, same-game/other-local-game device isolation, inherited eventbus noexcept/EAGAIN and supervisor allocation failure remain separate gates. A protected seat registry cannot establish these by itself. Do not claim bounded physical kernel/GPU termination, full exception-safe ingress, R1/R6 closure or deployability.

## Decision note — technical step 1 and subsequent explicit user choices

Manager authorized only additive checked-Xbox backend/owned-listener step 1 after reading this design; the earlier proposal remains historical. No InputSeat/coordinator/ingress/runtime enable is authorized by this step. Default-deny Unix injection without existing-grant delegation, queue 256 packets/64 KiB with reserved revoke, 5 s bounded decision and quarantine cap 1 were accepted as provisional **technical defaults**, not measured latency or direct user quotations; not implemented here.

User subsequently explicitly chose **“Только геймпад для первой версии”** and **“После выбора запущенного WoW на новом устройстве”**. Authoritative project docs commit `a896ab6`, `docs/{requirements,decisions}.md`; exact user source `wiki/raw/20261111-user-mvp-input-policy.md` in the Manager project.
